# 1000Mark

A benchmark for any computer or phone on one fixed scale, where 1000 is a fast desktop. Two tests share the same results pages: a browser test that needs no install, and a computer test (`native/`, Rust) that reads the real hardware. The computer test is the main product; a browser cannot see everything (some browsers report false thread counts and hide the graphics chip).

The code was called Pressmark before 2026-11-14, so internal names still say pressmark: the Rust crate (Cargo forbids a leading digit), the database file, localStorage keys, the `pm_session` cookie and `pmk_` keys. Everything people see says 1000Mark.

## Look
Three-ink screen print: cool grey paper, federal-blue key ink, fluoro pink, yellow and mint spot inks, flat blocks with hard offset shadows, dot screens, stamped squares ("lanes"), Anton for display type, Space Mono for labels, Archivo for text. Tokens are at the top of `style.css`. Keep it blocky: no rounded corners, no gradients except dot screens and hatching, no soft shadows.

Width: the page runs to 1680px. From 1440px long bar lists (`.bars.many`, 12 rows or more) go two-up and the balance chart takes three fifths of its row; text blocks keep a 65-character measure. The balance chart (`radar()` in `charts.js`) is a fine-line instrument, not a stamp: thin doubling rings with four finer rings between each pair, a solid ring at 1000, a translucent shape. On phones it draws a compact version with two-line labels.

Colour roles (tokens in `style.css`): `--ink` text, `--line` rules and outlines, `--paper` the sheet, `--surface` printed blocks, `--mark` data drawn in the key ink, `--on-spot` text printed on a spot colour, `--hero-*` the big score stamp, `--chip-*` filled tags, `--flood-*` / `--sh-*` / `--stamp-border` the part-score stamps. Dark mode follows printing on black stock: warm soft-black sheet, tone-on-tone panels, bone text ink, muted outlines, part-score stamps as solid floods with dark type, the system score as bare yellow type. Avoid thin bright outlines and near-white text in dark. Style components through these tokens only; never write a theme-specific component rule.

## Layout
- `index.html`, `style.css`, `app.js` (UI, run orchestration, pages), `charts.js` (bars, radar, columns, lanes), `scoring.js` (test list, reference values, weights).
- `tests/cpu.worker.js` (CPU and memory, running `tests/kernels.wasm`), `tests/storage.worker.js` (OPFS sync handles), `tests/gpu.js` (WebGPU, WebGL2 fallback), `tests/media.js` (WebCodecs encode/decode).
- `server/server.mjs` (accounts, run storage, leaderboard, percentiles, hand-off from the computer test), `server/admin.mjs` (support requests and unlocking accounts).
- No build step and no dependencies (`tests/kernels.wasm` is committed). `serve.py` serves the site alone (adds COOP/COEP headers).

## Rules that matter
- **Suite 1 is frozen (2026-11-14).** The tests, their workloads (`native/kernels`, the shaders, the storage and video tests) and every `ref`/`bref` in `scoring.js` are the scale. Never edit them and never add a scored test: Jordan wants one suite for good, so a run made today still compares in ten years without re-testing old machines. What can change freely: use cases, weights, size curves, pages (scores are computed at display time from stored raw results), and new tests marked `unscored`. Runs carry `suite: 1`; runs without it (pre-1.0) are set aside (`pressmark.runs.pre1` in localStorage, ignored by the server's leaderboard and percentiles).
- Scores: test = 1000 × result / reference; part = weighted geometric mean of its tests; system = weighted geometric mean of parts (weights in `scoring.js`). Speed is always linear: no diminishing returns. A use case weights parts, groups of tests (`groups`) and kinds of CPU work (`kinds`: apps, sim, media, maths).
- One test list for both tests. `ref` is the computer test's reference, `bref` the browser test's, both measured on the reference PC (browser = the Claude app's Chromium pane, visible), so that machine scores 1000 either way. A browser run says how fast the computer is through that browser.
- CPU and memory workloads are one Rust crate, `native/kernels`: real-program work (deflate, JSON, an interpreter, A*, a B-tree database, photo filters, a ray tracer, physics, matrix multiply, sorting), not tight toy loops, which undersold wide cores (the old tests put an M1 Pro 40% behind a 5950X on one core; these put it 8% ahead, as published benchmarks do). The computer test links the crate; the browser runs it as `tests/kernels.wasm` (built by `native/build-wasm.sh`, committed). Hardware crypto is the exception: `sha2` natively, `crypto.subtle` in the browser. The browser's block copy uses `TypedArray.set` because WebAssembly's `memory.copy` is a fifth of the speed in Chromium.
- CPU tests run on one core (`c1_*`), six threads (`c6_*`: games and everyday apps rarely keep more busy) and all threads (`ca_*`). Every timed test runs three times for 0.7 s and keeps the median.
- The computer test uses mimalloc on every system, so allocation-heavy tests measure the hardware and not glibc, macOS or Windows. One-core tests run on a spawned thread like the rest.
- Five scored parts: CPU, GPU, memory, storage speed and capacity. Capacity (`sz_ram`, `sz_vram`, `sz_drive`) scores through curves of `[GB, points]` anchors (`curvePoints()`, doubling scale, flat past the last anchor): `curve` on the test line is general use, and each use case in `PROFILES` has its own `sizes`. Every curve must give the reference machine's 32 GB, 10 GB of graphics memory and 4 TB exactly 1000. Graphics memory is the chip's own, or half of RAM where it is shared (integrated graphics, Apple silicon; `info.vramShared`). Which sizes count is set per use case in `groups.capacity` (a weight of 0 leaves a test out): memory size everywhere, graphics memory for games, AI, design, video, engineering and science, drive size only for the server score (Jordan, 2026-11-14: space is not speed and a drive is easy to add). Capacity exists only in computer-test runs. Browser storage tests (`sto_*`) are shown but not scored: browsers serve them from memory and their own databases.
- The computer test prints each result with its points as it finishes. It computes them from `scoring.js` itself (embedded and parsed in `main.rs`, `Scorer`, including the general `curve`), so keep that file's one-test-per-line format and the CATS weights equal to the General use weights. General use's group and kind weights stay at 1, except tests it leaves out, which carry `general: 0` on their line so the computer test's total leaves them out too.
- Storage: sequential tests move 64 MB per request over a 4 GB file written in three timed parts; random 4K tests run one at a time (`s_rand_*`) and 32 at once on 32 handles (`s_rand32_*`).
- GPU: the same WGSL in both tests. The computer test reads `SCENE`, `RT_COMMON` and `RAYS` out of `tests/gpu.js` (`js_shader()` in `gpu.rs`), and `rt_scene()` must build the same scene as `rtScene()` (a unit test checks the hashes; `cargo test`). `gpu_rt` traces the scene with ray queries (wgpu experimental, Vulkan only in wgpu 24, so on Windows it looks for the same chip through Vulkan); without ray-tracing hardware within reach the compute result stands in. `info.rayTracing` says which. The acceleration structure needs an index buffer: wgpu 24 builds garbage from unindexed triangles.
- Native GPU shaders are created with `create_shader_module_trusted` and no runtime checks: on Metal wgpu otherwise bounds-checks every buffer read. Keep every shader's own bounds checks and loop limits.
- GPU tests scale their batch until one batch takes about 40 ms (`loop()` / `gloop()`), timing each size twice and trusting the quicker go; a small batch measures the round trip to the GPU, not the GPU.
- Video (`vid_*`) goes through WebCodecs in both tests. The computer test has no video code: when its run reaches the results page without video results, `addVideo()` in `app.js` measures them there and adds them. A run made with `--json-only` or on a machine without a browser has no video results.
- Heat: `run.heat` (`mode` end or soak, `minutes`, `cpu`, `gpu`, `series`). Every run re-times a few all-core CPU tests and two GPU tests at the end and stores the share of cool speed kept. `--heat` (computer test) or "With heat test" (browser) first loads every core and the GPU together for 12 minutes, sampling as it goes. Heat never changes a score.
- Power (`run.power`: `cpuIdle`, `cpuOne`, `cpuAll`, `gpu`, `gpuIdle` in watts, plus sources; heat series entries carry watts as their 4th and 5th values) is read by `native/src/power.rs` where the system allows it without admin rights: Linux RAPL counters and NVIDIA/AMD cards, Apple silicon through IOReport (graphics chip only: on macOS 27 the processor's counters are frozen without admin rights, and a counter that does not move is reported as nothing), NVIDIA on Windows. Chip estimates, shown with points per watt, never scored.
- `sha2` needs its `asm` feature on aarch64 or it ignores the CPU's SHA instructions.
- Anything else running skews results (Jordan's screensaver alone halved every GPU score). The computer test warns when other programs use over 8% of the processor (`info.busy`). When measuring on Jordan's PC, close the screensaver and hold `systemd-inhibit --what=idle`.
- Everything needs a secure context (https or localhost): OPFS, WebGPU, WebCodecs and crypto.subtle are blocked on plain http.
- Runs are kept in localStorage (`pressmark.runs`), newest first, 400 kept; signed in, they also live in the account.
- Browser runs are hidden wherever computer-test runs exist, unless "Show browser tests" is ticked (`state.showBrowser`) or a browser test was just run. Never rank or compare the two kinds together by default.
- In the site's copy the native program is the "computer test", never "the app"; code and ids still say app/native.

## Pages
`#home` results (or the intro), `#cpu` etc. part pages, `#computer` how to run the computer test, `#devices` device names, types and the compare table, `#leaderboard`, `#signin`, `#register`, `#account`, `#support`. Account links sit at the top right; the main menu is its own bar under the logo and is where new sections go. The theme switch is in the footer.

Devices are grouped by name (`label`); a device can hold computer-test and browser runs. Renaming relabels its runs, and giving two devices the same name merges them.

Badges: the server works out who holds first place (`computeBadges()` in `server.mjs`) from the computer-test leaderboard, each person's best run, held-for-review runs excluded: Champion (highest system score), Gold (highest in each use case and each part), Silver (highest in each group of tests inside a part, skipped where the part has one group), Bronze (system score in the top 10% of people). Ties stay with the earlier run. The `badges` table keeps who holds each badge and since when; `boardChanged()` recomputes after every leaderboard change so the dates are right. `/api/leaderboard` returns `badges` keyed by username; `badgesFor()` in `app.js` draws one mark per tier beside a username (leaderboard, the account link in the masthead, the submit bar, the account page) with a hover or focus card saying why and for how long. Each tier has its own shape or texture (starburst, solid, hatched, dot screen) as well as colour.

Percentile view: a Points ⇄ Percentile switch. A percentile is the share of other machines a score beats, from `/api/population`: one anonymous row per machine (latest run of each account's device and test kind), scored on the server with `scoring.js`, cached 5 minutes. Compared with the same kind of test and a chosen kind of device (`device.formFactor`: phone, tablet, laptop, desktop or computer).

## Server (`server/server.mjs`)
- Node 22.13 or newer, no dependencies (built-in http, sqlite, crypto). Run it locally: `PORT=4273 HOST=127.0.0.1 DATA_DIR=<scratch folder> node server/server.mjs`. Outside production it makes its own keys file next to the data folder.
- Passwords: scrypt, at most three hashing at once. Emails: AES-256-GCM, with an HMAC fingerprint for lookups; the keys live in `KEYS_FILE`, never in the database or this repository. No IP addresses are stored.
- Sessions: random token in an HttpOnly, Secure, SameSite=Lax cookie; only its hash is stored. Bot check: a self-hosted proof-of-work puzzle on register, sign-in and support, plus a honeypot field and rate limits. Changes need JSON and a same-origin Origin header.
- Sign-in lockout: five wrong passwords lock an email for an hour, five more for a day, five more until a support request is answered (`admin.mjs unlock`). Emails without accounts lock the same way, so the lock does not reveal who has an account.
- Score checks: `implausible()` refuses runs that mix test kinds, exceed 25 times the reference on any test or 12 times on the system score, or claim more multi-core speed than the threads allow. `outliers()` holds back runs over 1.6 times the median of at least five others on the same chip from the leaderboard and percentiles.
- Security headers on every response (CSP, frame denial, HSTS). Static files: browsers revalidate (ETag), Cloudflare's edge caches for five minutes.
- The static file list is an allowlist (`ALLOWED`); add new site files there and to `SITE` in `native/src/main.rs`.
- Computer-test hand-off: the finished run is POSTed to `/api/handoff` (no sign-in, kept a day) and the site opens at `#claim=TOKEN`; the run is saved to the account now or on sign-in.

## Computer test (`native/`)
- Rust, one binary plus the `kernels` crate (`native/kernels`, the shared CPU and memory workloads; a workspace member): `cpu.rs`, `mem.rs`, `storage.rs` (direct I/O), `gpu.rs` (wgpu: Vulkan/Metal/DX12, same WGSL shaders as `tests/gpu.js`), `main.rs` (hardware detection, results file, hand-off, a fallback results page on localhost:4174).
- Flags: `--name --dir PATH --server URL --local --show-data --no-open --json-only --port N --connect KEY --disconnect --heat --minutes N`.
- What it sends: hardware model names and sizes, test results, laptop or desktop. Never the computer's name, user name, folder names or volume names (`device_name()` names the device after its processor).
- Build: `cd native && cargo build --release`. The site files are embedded with `include_str!`, so rebuild after changing the UI.
- Both tests use the same test ids. The binary writes raw per-second rates; `normalise()` in `app.js` converts them once (`norm: true`).
- Releases: pushing a `v*` tag builds all four platforms, attaches them with SHA-256 sums and build provenance to a GitHub release. The site's download links point at the latest release.
